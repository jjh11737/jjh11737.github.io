### 关于过程

我们约定：

- `x10` ~ `x17`：这8个寄存器负责参数传递和返回值
- `x1`：返回地址寄存器
- `x5` ~ `x7`/ `x28` ~ `x31`：临时寄存器，调用者保存
- `x8` ~ `x9` / `x18` ~ `x27`：被调用者保存寄存器



比如如果我们想实现一个递归嵌套过程：
```c
long long int fact (long long int n){
    if (n < 1) return 1;
    else return (n * fact(n-1));
}
```

那么它的汇编：
```assembly
fact:
	addi sp, sp, -16		// stack for return addr and argument n, these are all needed when returned
	sd	x1, 8(sp)			// return addr
	sd	x10, 0(sp)			// n
	addi x5, x10, -1
	bge x5, x0, L1			// n-1 >= 0, jmp2L1, prepare to call the target function
	
	addi x6, x10, 0			// mov the returned val to x6
    ld x10, 0(sp)			// restore n
    ld x1, 8(sp)			// restore return addr
    addi sp, sp, 16			// restore the stack pointer
    mul x10, x10, x6		// return n * fact(n-1)
    jalr x0, 0(x1)
L1:
	addi x10, x10, -1		// set n-1 as the argument to be passed
	jal x1, fact			// call fact
```

### 2.10 并行性与指令：同步

我们需要同步来防止data race，我们会使用**加锁(lock)**和**解锁(unlock)**来实现同步操作，而这可以用于创建一个同一时刻只允许一个处理器的一个执行流进入的区域（这实际上还是通过atomic来实现的，当然atomic真正保证了相关操作不会被并发执行流观察为拆开的，而实际上决定多核之间不出现冲突的还是缓存一致性协议，因为每个都有一套cache，需要保证它们对同一个内存位置的状态保持一致），也就是**互斥区(mutual exclusion)**

而在多处理器实现同步的关键是一组能够提供原子方式读取和修改内存单元的能力的硬件原语（ISA提供的），这样我们就能**保证在内存单元的读取和写入不会被插入任何其他的操作而打断。**

我们从 **原子交换(atomic exchange / swap)** 说起，它是构建同步机制的一种典型操作，用于将寄存器的值和存储器中的值交换

而具体来说，比如我们想构建一个锁变量，那么处理器就会尝试把寄存器里面的1和内存地址的值交换：

- 寄存器获取到0 那就是没加锁！那么很好，我们就获得锁了，而此时内存里面对应1代表占用
- 寄存器获取到1,那就说明被占用

关键在于交换是不可分割的，硬件会对两个同时发生的交换进行排序

> 但是我们还是要说，多处理器的关键在于cache coherence，也就是说当一个处理器想要执行exchange的时候，它必须先获得这个cache line的独占权限，如果获取到了，那么别的同样缓存了这个内存地址的数据的处理器对应的cache line就会被标记无效，它就必须要再次获取，此时才能去进行相应的操作

另一种方法是使用**指令对**（这还是ISA层面规定的），其中第二条指令返回一个值，然后通过分支跳转的指令来决定要不要重试（当然了处理器本身才不在乎呢）。只要任何处理器执行的所有其他操作都发生在该对指令外面，那么这就是原子的

而在RISC-V中，对应的就是**`lr.w`(保留加载-load reserved)** / **`sc.w`（条件存储-store conditional)**，它干的事情是：如果保存加载指令指定的内存位置的内容和条件存储指令看到的值不一样，那么指令就会失败不会写入内存

> 而关键在于lr.w之所以叫reservation，就说明这个hart会监视这块缓存，如果别的核也写入了同样的内存位置，那么缓存一致性协议就会让这个reservation失效，而如果是自己写那么写的时候就会失效了

一般汇编如下：

```assembly
again: 	lr.w x10, (x20)
		sc.w x11, x23, (x20)
        bne x11, x0, again
```

指令对的优点就在于我们可以更方便地构建原语，这是它的灵活性带来的好处

比如我们想要实现一个自旋锁：

```rust
		addi x12, x0, 1
again: 	lr.w x10, (x20)
		bne x10, x0, again		// 读不到0我就再读一遍
		sc.w x11, x12, (x20)
		bne x11, x0, again
```

具体的实现是A扩展











## 第3章 算术运算

基础的加法器自然不必多说，不过实际上我们可以考虑并行地完成加法的计算？而不是一定要按顺序地等待也就是纹波加法器那种。

### 加减法

#### CLA

我们仔细想一下，不能并行本质原因在于我们需要进位，而一般的加法器我们必须知道上一位的结果才能知道这一位要不要加上进位，这极其低效，因而我们分析一下进位本身：
$C_1 = X_1 Y_1 + (X_1 + Y_1) C_0$ ，满足这样的递推关系，而我们可以进一步代入展开：
$C_2=X_2Y_2+(X_2+Y_2)C_1=X_2Y_2+(X_2+Y_2)X_1Y_1+(X_2+Y_2)(X_1+Y_1)C_0$，,以此类推，显然我们发现实际上我们需要的只有$P_i=X_i+Y_i$，$G_i=X_iY_i$这两个是我们需要的数据，而进位本身是可以满足递推关系的，化简后是：
$$
C_1=G_1+P_1C_0 \\
C_2=G_2+P_2G_2+P_2P_1C_0 \\
C_3=G_3+P_3G_3+P_3P_2G_1+P_3P_2P_1C_0 \\
...
$$
只要$C_0$和$X_iY_i$同时到达，我们几乎就可以同时算出所有的进位！那么各位的计算就是并行的了，实现这种功能的电路称为先行进位器(Carry Lookahead Unit，CLU)，而这样实现的就是全先行进位加法器(Carry Lookahead Adder，CLA)

> 这看起来似乎很美好...但是实际上位数越多就需要对应的与运算，因为多位的与运算是级联的，我们发现这好像也没有改变关键路径的长度。。。似乎还是$O(n)$？而且更糟糕的是，这太浪费硬件了... 因此实际上我们实际设计里面不会简单地直接连接...而想要改变这一点，就是所谓prefix adder了，这种我们为什么不能用树的结构呢？

但是仔细一想，这肯定还是不够好的... 因为我们不是单独做好几个不同数的加法，我们是计算同一个数的移位的加法啊...

##### booth

这就要引入我们的booth算法了！我们为什么一定要做这么多次移位的产物？有没有什么方法我们保证能确定用更少的？因为我们可以发现似乎这总是有一个上限的，一旦位数过多，我们总是可以用更好的方法取代它，就像：0111 不就是1000 - 0001吗？

一种很朴素的想法是：我们可以找连续的1 ，然后把它转化为一个单独的1和一个减法，这很蠢，因为没法有对应的硬件实现。那么换一个思路，我们可以在一个局部的空间里面确定吗？

我们首先可以想到，对于一串连续的1 ，我们压根就不需要关注那些中间的1... 因为只有1到0的转换我们才关心，不是吗？那么我们可以这样想：

- 找到01代表这个位置有一个+A
- 找到10代表这个位置有一个-A

那么这就是所谓`radix-2`了，但是既然可以这样，那为什么不我们一次多看几位？也就是说我们把相邻的两个booth bit合并，那么我们可以想到radix4是什么样的：

公式是：$d_i = b_{2i} + b_{2i-1} - 2b_{2i+1}$

这实际上很好推导，我们从radix-2出发，我们已经知道一个booth bit的计算实际上就是：
$$
c_i = b_{i-1} - b_i
$$
那么我们想要两个一起看，就是
$$
d_i = 2c_{2i+1} + c_{2i} \\
d_i = 2(b_{2i} - b_{2i-1}) + (b_{2i-1} - b_{2i})
$$
那么写成表就是：

| 数字 | 产生结果 |
| ---- | -------- |
| 000  | 0        |
| 001  | +A       |
| 010  | +A       |
| 011  | +2A      |
| 100  | -2A      |
| 101  | -A       |
| 110  | -A       |
| 111  | 0        |

先对数字右侧补零，然后每次这个窗口左移2位，这样我们就可以直接确定移位

既然如此，那么我们其实只需要一般的partial product就能完成任务，这个树因此可以进一步压缩

### 4.6 流水线概述

本质：通过各级之间加上一层寄存器（往往会加上有效位），我们得以让每个阶段的单元只需要关注自己下一步要做什么，这好处最大就体现在我们的关键路径变短了，因为两个时钟周期之间我们只需要跑完一级流水线的内容就可以了

而对于RISC-V来说，它由于指令长度相同（除非你用了C扩展），自然取指和译码就大大简化了，而且存储操作数只出现在load和store指令里面，这样的好处就是我们可以执行单元搞定后直接交给访存单元

> 而实际在各级间寄存器传递的正是一个指令执行所需要的状态（后续单元需要的），同时为了保证不冲突，应该标注寄存器是否有效，比如valid和ready，前者告诉下一级流水线是否可以用这个数据，后者告诉上一级流水线是否可以传递数据，如果下一级不能ready则上一级也不能

### 结构冒险struct hazard

硬件不支持多条指令在同一时钟周期执行

### 4.8 数据冒险 data hazard

也就是我们指令之间出现数据依赖，这是最关键的问题。就比如：
```assembly
add x19, x0, x1
sub x2, x19, x3
```

显然后一条依赖于前一条计算的结果，因为如果没有别的数据通路，我们需要等到add执行到第5个周期写回才能让sub执行，这会阻塞流水线

解决方法是两种：**前递(forwarding)** 或 **旁路(bypassing)**

前递有好处，但是显然它不能解决所有问题

> 就比如load-use hazard：我们`lw`后再`add`，只有到访存时才能知道这条指令写回的结果，但是偏偏我们下一条指令就需要用，如果没有别的机制就只能等待。那么此时我们就得停顿，称为**流水线停顿(pipeline stall) / 气泡bubble**（正因此，我们的编译器和处理器才会对指令进行重排来尽可能避免这种情况）
>
> 例如：针对标准的五级流水线，我们考虑以下C代码：
>
> ```c
> a = b + e;
> c = b + f;
> ```
>
> 生成的asm：
>
> ```asm
> lw

### 4.9 控制冒险

也是我们控制流取决于我们的条件语句，我们一条branch指令之后需要考虑下一个时钟周期的指令，但问题是当前我们的流水线才刚刚完成取指，也就是说我们也不知道下一条指令是什么!

一种方法就是暴力的方法，停顿，或者说我们加入足够多的硬件来在流水线的ID阶段就完成测试寄存器+计算分支目标地址+更新PC，但很显然，流水线一长这件事几乎不可能，而如果每次都停顿，性能会严重下降

 那么就是第二种方法，预测。但是很显然，出错了我们就需要冲刷流水线

那么首先是分支预测的策略，一种最简单的方法就是：总是预测不会跳转。

更成熟的预测方法是，我们分别采用不同的方式应对，比如一种简单的方法是针对循环，因为最后一句必然是条件分支指令，所以我们可以预测会发生分支并跳转到前面



而想要丢弃指令，只需要将初始控制值变为0即可，比如branch指令如果发现预测错误就需要清除EXU之前的所有阶段的指令。可以插入NOOP，比如`addi x0, x0, 0`，当然更好的设计实际上是给流水线间的寄存器增加一个有效位，只有valid时才产生作用



##### 缩短分支延迟

很显然，另一种方法就是我们更早地执行掉条件分支指令，我们在IF和ID阶段已经拿到了当前的PC和立即数，而麻烦主要也就在决定分支本身：**需要比较寄存器中的值**，但是偏偏我们分支依赖的寄存器数据可能还在流水线当中。当然可以通过前递来尝试解决。





##### 动态分支预测

动态硬件预测器根据每个条件分支指令的行为进行预测，并且在程序生命周期内可能会改变条件分支的预测结果。例如：使用最近成功的预测调整下一次的预测

比如一种常见的实现方法是我们保存每个条件分支是否发生分支的历史记录，然后根据最近过去的行为预测未来。也就是采用**分支预测缓存** / **分支历史表**





### 4.10 例外

控制逻辑的设计是最麻烦的部分，例外和中断是控制逻辑需要实现的任务之一

> 多数体系结构设计者和相关书籍并不区分二者
>
> 这里用**例外**指代**意外的控制流变化（不关注变化来自于处理器内部还是外部）**，是同步事件
>
> 而用**中断** **仅仅**指代**由处理器外部事件引发的控制流变化**，是异步事件

而麻烦的是，检测和处理例外的控制逻辑需要处于处理器时序的关键路径上，会对处理器的主频和性能造成影响！

> 因此设计时需要对此给予充分重视













#### RISC-V体系结构如何处理例外

目前所讲的实现中，只存在2种例外类型：未定义指令和硬件故障，不过RISCV对所有的例外和异常都统一用`trap`来指代

流程：

1. 当例外发生时，处理器至少需要先在**系统例外程序计数器SEPC**里面保存发生例外的PC
2. 将控制权移交给OS，比如`ecall`
3. 之后OS将会继续调用对应例程完成操作

而显然在第二步，讲控制权移交给OS时需要附带说明例外发生的原因以便OS确定需要执行的例程，有两种方法：

- **向量式中断(vectored interrupt)**，将原因作为偏移加到基址寄存器上，通过查询中断向量表来完成控制流的转换，也就是x86之类的使用的方法
- **设置系统例外原因寄存器SCAUSE**，也是RISC-V使用的方法

> 而设置这些的工作就会在处理器碰到Trap时自动完成，例如处理器执行到`ecall`的时候，硬件会自动完成CSR的设置，之后进入S-mode并通过stvec跳转到OS的例程移交给内核处理
>
> 相关的寄存器约定见priviledged spec手册，[priv-csrs](https://docs.riscv.org/reference/isa/v20260120/priv/priv-csrs.html)

#### 流水线中的例外

在流水线实现中，将例外程序视为另一种控制冒险即可

例如若执行`add`指令时发生硬件故障，我们就需要在流水线上清除`add`之后的指令并从新的地址开始取指。不同于分支指令的是，例外会引起系统状态的变化





### 4.11 指令级并行

像流水线就是挖掘了指令间存在的潜在的并行性，这种并行就被称为所谓**指令级并行ILP**。

而提高ILP主要有两种主要手段：

- **更多的流水线级数**，也就是说我们可以把关键路径里面相关操作最长的进一步细分从而减小关键路径

- **多发射(multiple issue)**，也就是增加流水线内部的功能部件数量，这样每周期就可以发送多条指令

  由此，我们的CPI实际上可以小于1！

  而实现多发射处理器有两种主要方法：

  - **静态多发射**：指令的发射与否在编译时完成
  - **动态多发射**：动态执行的过程中由硬件完成

  而在多发射流水线中，需要处理如下两个主要任务：

  - 将指令打包进入**发射槽**。

    关注：处理器如何判断本周期发射多少条指令 / 发射哪些指令

    在静态发射处理器中，编译器会完成这部分工作，而在动态发射处理器中，编译器可以指令重排来提高发射效率，工作主要在运行时由硬件自动完成

  - 处理数据和控制冒险

    在静态发射处理器中，编译器静态处理量部分/所有指令序列中存在的数据和控制冒险。

  >  虽然这么分类，但是实际上二者的界限并没有那么模糊，就像上文提到的，超标量也可以通过编译器辅助来进一步挖掘并行性

#### 4.11.1 推测

推测是另一种很重要的挖掘指令级并行的方法。

它**允许编译器 / 处理器来猜测指令的行为**，并允许其他与被推测指令相关的指令提前开始执行。

> 最经典的就是分支预测，可以提前执行分支指令之后的指令
>
> 又比如对于RAW，可以推测两条指令的访存地址不同从而允许load先于store执行

而推测的难点在于推测的结果可能出现错误，因此任何推测机制都必须包含：

- 预测结果正确性的检查
- 预测出错后的恢复机制

而难点在于：

1. 实现错误时的恢复机制非常困难。

   在软件实现的推测中，编译器经常需要插入额外的指令来检查推测的正确性，并在检测到推测错误时提供例程进行恢复

   而在硬件推测执行时，处理器通常会保存推测结果知道推测被确定是正确的。推测错误需要对流水线进行恢复 / 停顿，会降低性能

2. 对某条指令的推测可能会引入不必要的例外

   比如一条访存指令如果本身处于推测执行，同时访存地址本身发生了越界，偏偏还预测错误了，就会引发本不该发生的意外。

   这就非常复杂了，需要添加额外的支持，对此类意外一直延迟响应知道确认推测正确

#### 4.11.2 静态多发射

静态发射器需要编译器来支持指令打包和处理指令间的冒险。将同一周期发射出去的发射指令包看作一条需要多种操作的大指令。这正符合**超长指令字(VLIW)**的设计思路



比如一个静态多发射的RISC-V处理器：

先考虑一个简单的双发射RISC-V处理器，其中指令序列中的一条指令是定点ALU指令  / 分支指令，另一条指令是访存指令。而如果指令当中的一条无法发射，则需要将其替换为nop

而对于潜在的数据/控制冒险，有不同的解决方案。
我们当然可以图省事直接完全让编译器代劳不关心冒险检测 / 流水线停顿的产生。
但是更负责的还是需要使用硬件检查两个指令包之间的数据冒险并产生响应的流水线停顿，编译器只负责在单个指令包中检查所有类型的相关。
但即便如此单个冒险也会导致整个指令包的发射停顿... 

如果想同时发射ALU和数据传输类指令，那么首先需要添加的就是寄存器堆的读写口了。同时由于ALU只负责ALUop的执行，所以访存还需要单独的加法器来计算地址。（否则会引入大量的结构冒险）

这种双发射处理器最多可以提高两倍的性能，但同时也需要程序中存在两倍的可重复执行指令的数目。而重叠执行本身又会因为更多的数据/控制冒险而导致性能损失。同时另一方面如果指令包内存在数据冒险，那么其中一条就被迫无法发射，原本不存在使用延迟的ALU也被迫可能会引入使用延迟。

而关于调度，看看这个例子：

```asm
loop: 	lw 	x31. 0(x20)
    	add x31. x31. x21
    	sw x31. 0(x20)
    	addi x20. x20. -4
    	blt x22. x20. loop
```

该如何把它们放入指令包呢？显然，前3条存在数据依赖没法放在一起（不过我们可以修改指令里面的常量），显然后两条不是很重要，把它们可以插入前面的指令中：（注意我们只有一套ALU... ）

|       | ALU/B                | LS                   | cycle |
| ----- | -------------------- | -------------------- | ----- |
| Loop: |                      | `lw 	x31. 0(x20)` | 1     |
|       | `add x31. x31. x21`  |                      | 2     |
|       | `addi x20. x20. -4`  |                      | 3     |
|       | `blt x22. x20. loop` | `sw x31. 0(x20)`     | 4     |

而这里我们就可以更好地理解**循环展开**了，通过将多个循环的事情放到一轮完成，由于轮间并没有直接的数据依赖，就可以更好地填入指令包而不必忍受那么多nop，比如前面那个程序我们把循环体展开4遍，不仅减少了循环开销还能提高并行性：

> 我们先说明寄存器分配：第一次循环是x31，直到x28
>
> 然后同样考虑数据依赖，我们必须在访存指令后等待1个周期空着才能使用这个寄存器！所以add必须在lw后等一个周期。而`sw`当然是等的越久越好了
>
> 而循环开销，很显然4轮循环的`addi`可以合并在一起，`blt`也只需要一条.

|       | ALU/branch           | L/S                   | cycle |
| ----- | -------------------- | --------------------- | ----- |
| Loop: | `addi x20. x20. -16` | `lw 	x31. 0(x20)`  | 1     |
|       |                      | `lw 	x30. 12(x20)` | 2     |
|       | `add x31. x31. x21`  | `lw 	x29. 8(x20)`  | 3     |
|       | `add x30. x30. x21`  | `lw 	x28. 4(x20)`  | 4     |
|       | `add x29. x29. x21`  | `sw x31. 16(x20)`     | 5     |
|       | `add x28. x28. x21`  | `sw x30. 12(x20)`     | 6     |
|       |                      | `sw x29. 8(x20)`      | 7     |
|       | `blt x22. x20. loop` | `sw x28. 4(x20)`      | 8     |

这里使用了**寄存器重命名**，其目标是除了真数据相关，消除指令间存在的其他相关。也就是**反相关** / **名字相关(name dependence)**，比如我们如果展开都用同样的寄存器命名，就会因为名称复用产生本不存在的依赖。而把它们分配给不同的寄存器就可以避免这一点



#### 4.11.3 动态多发射

也就是所谓的超标量了。

在最简单的超标量处理器中，指令按序发射，由硬件判断当前周期可以发射的指令数

但即使需要编译器配合，和VLIW的根本区别在于：

- **不论软件调度与否硬件都必须保证代码运行的正确性**

- 编译生成带的运行正确性应与发射率 / 处理器流水线结构无关

  > 但在VLIW里面代码需要重新编译才能正确运行在不同的处理器实现上，可以说对编译器的要求是灾难性的...

许多超标量处理器扩展了动态发射逻辑的基础框架，形成了**动态流水线调度**技术：由硬件逻辑选择当前周期内执行的指令，并尽可能避免流水线的冒险和停顿。

> 比如下面这段代码序列：
>
> ```asm
> lw    x31, 0(x21)
> add   x1,  x31, x2
> sub   x23, x23, x3
> andi  x5,  x23, 20
> ```
>
> `sub`指令完全可以更早开始执行，尤其是`lw`访存如果发生cache miss那可就太糟糕了！硬件做的事情就是对指令序列重排

##### 动态调度流水线

动态调度流水线由硬件选择后续执行的指令，并且对指令进行重排来避免流水线stall

在这样的处理器里面流水线会被划分为这些部分：**取指和发射单元 / 多功能部件 / 提交单元**

简单的示意图如下：

![image-20261111142158789](https://raw.githubusercontent.com/jjh11737/jjh-blog-images/master/imgs/image-20261111142158789.png)

- 每一个功能单元前有若干个缓冲区，称为**保留站**，存放指令的操作和所需的操作数
- 只要缓冲区中的指令所需的操作数准备好，并且功能单元就绪，就可以执行指令
- 指令执行结束，结果将会被传送给保留站中正在等待使用该结果的指令+ 提交单元保存
- 提交单元保存好已完成指令的执行结果，并在指令真正提交时才使用它们更新寄存器。
- 这些位于提交单元的缓冲区就是**ROB(重排序缓冲reordering buffer)**
- 和静态流水线的前递逻辑一样，ROB也可以为其他指令提供操作数

保留站和重排序缓冲共同提供了一种寄存器重命名的方式，它有点像我们之前说的编译器使用的技术：

1. 发射指令时，指令会被拷贝到相应功能单元的保留站内。

   同时，如果它所需要的操作数也已经准备好，也会从寄存器堆 / 重排序缓冲中拷贝到保留站

   指令会一直保存在保留站中，直到所需的操作数全部准备好且相应的功能部件可用

   由于可用的操作数此时已经拷贝到工作站里面了，那么它们在寄存器堆中的副本就无须保存了，如果此时出现了响应的寄存器写操作那么寄存器的值就会被更新

2. 如果操作数不在寄存器堆和ROB中，那么它就一定在等待一个功能单元的计算结果。它的名字将会被记录，等最终结果计算完毕就会被直接拷贝到等待结果的保留站里面，旁路了寄存器堆

从概念上看，<u>可以把动态调度流水线看作**程序的数据流分析**</u>。我们在保证程序对外数据流顺序的一致性的前提下以某种顺序执行指令，就称为**乱序执行**。（因为取指和执行顺序不同）

而为了使得程序行为和与简单的按序单发射流水线一致，乱序执行流水线的取指和译码也都需要按序进行，以便正确处理指令间的相关。也就是所谓**按序提交**



而更高级的动态调度技术还包含了基于硬件的推测式执行：

- 通过预测分支指令的转移方向动态调度器就可以沿着预测路径不断地取指和执行，由于指令都是按序提交的，在它们被提交前就已经知道了分支预测正确与否。
- 甚至对于load指令之类的访存地址也可以推测，也就是说`load / store`也可以乱序执行，并使用提交单元来避免不正确的推测



但是另一方面，乱序执行会引入新的流水线冒险，当两条指令使用相同的目标寄存器 / 存储地址时会发生名字相关，但这两条指令间却不存在数据流。比如在程序顺序中，指令i位于j之前，二者之间可能会存在两种类型的名字相关：

1. **反相关(anti-dependence)**：当指令j写入指令i读取的寄存器 /内存位置时，就认为存在反相关，WAR
2. **输出相关**：也就是两个都写入同一个位置，WAW

当然了我们会使用更加直观的名字：

1. 反相关导致WAR(Write-After-Read)冒险
2. 输出相关导致的WAW冒险
3. 真数据相关导致的RAW冒险

而前两者就是简单顺序流水线里面不存在的，乱序会导致产生这种伪相关



而既然编译器也能通过指令调度来解决数据相关，为什么我们还是需要在超标量处理器里面实现动态预测技术？主要有3个原因：

1. **并非所有的流水线停顿都是可预测的。**

   比如最常见的访存如果cache miss那么流水线就会产生不可预测的停顿，而动态调度就允许我们通过执行别的指令来隐藏停顿（这也正是高明之处，一条指令只有它的资源就绪才能被执行）

2. 如果处理器中使用了动态分支预测计数，实际上我们在编译时是无法得知指令真实的执行顺序的，因为取决于实际的分支预测结果和执行结果，不可能完全解决分支问题

3. 也是最直观的，我们可以对外隐藏微结构实现的细节。

   很显然，不同的处理器实现会有不同的延迟和发射宽度，会改变编译代码的最佳配置，而我们不可能为了每一个硬件实现去配置单独的编译器后端。同时旧的代码无须重新编译即可运行在新的硬件实现上



同时另一方面，尽管现代高性能处理器可以单周期发射多条指令，但是一直保持高发射率是困难的，主要原因如下：

- 流水线内部的性能瓶颈主要在于指令间的依赖关系。而这种依赖关系无法消除，自然就会降低指令间的并行性和发射率。而最大的问题是编译器有限的能力可能会导致有一些并非真正的数据相关产生，比如指针常常会引入存储器别名，这就会引入潜在的数据相关。而另一方面哪些无法在编译时 / 运行时准确推测出跳转方向的分支指令将会对
- 缓存层次的各级失效(miss)也会让流水线无法满负荷运转，实际上这也正是最大的问题，访存的速度太慢太不确定了！各种机制实际上都在试图帮我们隐藏这部分的延迟











#### 4.11.4 能效和高级流水线

> 正在看
